# ToDo List в Docker
проверка
## Описание проекта

Веб-приложение `ToDo List` реализует хранение и обработку задач, а также отправку и проверку писем по почтовым протоколам. Проект подготовлен для лабораторных работ №3 и №4 и состоит из нескольких независимых компонентов:

- `UI` — пользовательский интерфейс;
- `Back` — серверная часть с REST API;
- `DB` — база данных PostgreSQL;
- `Mail Server` — локальный почтовый сервер для SMTP, IMAP и POP3.

Все компоненты запускаются в отдельных Docker-контейнерах и взаимодействуют через общую Docker network.

## Теоретическая часть

### Теория Docker и контейнеризации

Docker представляет собой платформу для разработки, доставки и запуска приложений в изолированной среде. Основная идея Docker заключается в упаковке приложения вместе со всеми его зависимостями в контейнер. Такой подход позволяет запускать приложение одинаково на любой машине, где установлен Docker.

Контейнер является изолированным процессом, который использует ядро операционной системы хоста, но при этом имеет собственное файловое окружение, сетевые настройки и список процессов. В отличие от виртуальной машины, контейнер не содержит полноценной отдельной операционной системы, поэтому запускается быстрее и потребляет меньше ресурсов.

Контейнеризация решает несколько задач:

- устраняет различия между средами разработки и запуска;
- упрощает развертывание приложений;
- делает архитектуру более модульной;
- облегчает переносимость проекта;
- позволяет запускать разные части системы независимо друг от друга.

В данной работе контейнеризация особенно важна, поскольку приложение состоит из нескольких логически отдельных частей: интерфейса, серверной логики, базы данных и почтового сервера. Каждая часть запускается как отдельный сервис, но при этом остаётся частью одной общей системы.

### Образ и контейнер

В Docker необходимо различать два понятия:

- `Docker image` — шаблон, по которому создаётся контейнер;
- `Docker container` — запущенный экземпляр образа.

Образ содержит инструкции, файлы приложения, конфигурацию и зависимости. Контейнер создаётся на основе образа и является его рабочей копией во время выполнения.

Например, образ backend содержит ASP.NET-приложение и среду выполнения .NET, а контейнер backend запускает API и слушает HTTP-запросы на определённом порту.

### Docker network

Docker network используется для организации взаимодействия между контейнерами. После подключения контейнеров к одной сети каждый контейнер может обращаться к другому по имени.

В данной работе используется сеть:

```powershell
docker network create todo-network
```

После этого:

- backend обращается к PostgreSQL по имени `todo-db`;
- backend обращается к почтовому серверу по имени `todo-mail`;
- пользователь открывает UI через `localhost`, а UI отправляет HTTP-запросы к backend.

Таким образом, Docker network заменяет ручную настройку IP-адресов и делает систему более устойчивой к перезапуску контейнеров.

### Основные Docker-команды

Для работы с проектом используются базовые Docker-команды.

`docker build` предназначена для сборки образа:

```powershell
docker build -t todo-back .
```

`docker run` используется для запуска контейнера из образа:

```powershell
docker run -d --name todo-back --network todo-network -p 5000:5000 todo-back
```

`docker ps` выводит список запущенных контейнеров:

```powershell
docker ps
```

`docker rm -f` удаляет контейнер:

```powershell
docker rm -f todo-back
```

`docker logs` показывает журнал работы контейнера:

```powershell
docker logs todo-back
```

`docker network create` создаёт пользовательскую сеть:

```powershell
docker network create todo-network
```

`docker images` показывает список собранных образов:

```powershell
docker images
```

Эти команды позволяют собрать, запустить, проверить и пересобрать все компоненты системы.

### Структура Dockerfile

`Dockerfile` представляет собой текстовый файл с инструкциями по сборке Docker-образа. Он описывает, из какого базового образа строится контейнер, какие файлы копируются внутрь, какие команды выполняются и как приложение запускается.

Наиболее важные инструкции:

- `FROM` — указывает базовый образ;
- `WORKDIR` — задаёт рабочую директорию внутри контейнера;
- `COPY` — копирует файлы в контейнер;
- `RUN` — выполняет команду при сборке образа;
- `ENV` — задаёт переменные окружения;
- `EXPOSE` — документирует используемый порт;
- `ENTRYPOINT` — определяет основную команду запуска контейнера.

Пример структуры backend Dockerfile:

1. Выбор базового образа .NET SDK для сборки проекта.
2. Копирование `.csproj` и восстановление зависимостей.
3. Копирование исходного кода.
4. Публикация приложения в Release-режиме.
5. Использование более лёгкого runtime-образа для запуска.
6. Настройка порта и старт приложения.

Такой подход называется multi-stage build. Он позволяет уменьшить итоговый размер контейнера, так как финальный образ не содержит лишних инструментов сборки.

### Архитектура веб-приложения

Современное веб-приложение обычно строится по модели разделения обязанностей:

- фронтенд отвечает за отображение интерфейса и действия пользователя;
- бэкенд обрабатывает запросы, реализует бизнес-логику и взаимодействует с внешними сервисами;
- база данных хранит информацию;
- дополнительные сервисы, например почтовый сервер, выполняют специализированные задачи.

В данной работе архитектура является многокомпонентной:

- `nginx` отдаёт статический HTML/JavaScript интерфейс;
- `ASP.NET Core Web API` обрабатывает REST-запросы;
- `PostgreSQL` хранит таблицу задач;
- `GreenMail` эмулирует почтовый сервер для SMTP, IMAP и POP3.

Такое разделение делает приложение ближе к реальной промышленной архитектуре.

## Теория работы API и обмена данными

### REST API

REST API представляет собой способ взаимодействия клиента и сервера по HTTP. Каждое действие выполняется через определённый HTTP-метод и URL.

В проекте используются следующие методы:

- `GET /api/Tasks` — получить список задач;
- `GET /api/Tasks/{id}` — получить задачу по идентификатору;
- `POST /api/Tasks` — создать задачу;
- `PUT /api/Tasks/{id}` — изменить задачу;
- `DELETE /api/Tasks/{id}` — удалить задачу;
- `POST /api/Email/send` — отправить письмо по SMTP;
- `GET /api/Email/check-imap` — проверить почту через IMAP;
- `GET /api/Email/check-pop3` — проверить почту через POP3.

### Как передаются данные

Обмен данными между UI и backend происходит через HTTP-запросы. Во frontend используется `fetch`, который отправляет запрос на API. Сервер получает запрос, обрабатывает его и возвращает ответ в формате JSON.

Пример логики работы:

1. Пользователь нажимает кнопку добавления задачи.
2. JavaScript формирует `POST`-запрос с JSON-объектом задачи.
3. Backend получает объект, сохраняет его в базе данных через Entity Framework Core.
4. Сервер возвращает ответ, после чего UI запрашивает обновлённый список задач.

По такому же принципу выполняются просмотр, редактирование и удаление.

### Взаимодействие backend и базы данных

Backend использует `Entity Framework Core` и `DbContext`. Контекст базы данных описывает таблицу `Tasks` как `DbSet<TodoTask>`.

При выполнении API-запросов:

- данные читаются из PostgreSQL;
- преобразуются в объекты C#;
- изменяются при необходимости;
- сохраняются обратно в таблицу.

Это позволяет работать с базой данных на уровне моделей, а не вручную формировать SQL-запросы в коде контроллеров.

### Работа почтовых протоколов

Для лабораторной работы №4 были использованы три почтовых протокола:

- `SMTP` — протокол отправки писем;
- `IMAP` — протокол доступа к сообщениям на сервере;
- `POP3` — протокол получения писем с сервера.

В проекте backend подключается к локальному почтовому серверу `GreenMail`.

Логика работы следующая:

1. Пользователь выбирает задачу и вводит адрес `test@local`.
2. Backend формирует письмо и отправляет его через SMTP.
3. Письмо попадает в локальный почтовый контейнер.
4. При нажатии на кнопку `Проверить IMAP` backend подключается к тому же контейнеру по IMAP и получает список писем.
5. При нажатии на кнопку `Проверить POP3` backend подключается к тому же контейнеру по POP3 и получает письма другим протоколом.

Таким образом, отправка и приём почты тестируются в полностью локальной среде, без использования внешних почтовых сервисов.

## Использованные команды

### Сборка образов

```powershell
docker build -t todo-back .
docker build -t todo-ui -f .\wwwroot\Dockerfile.ui .\wwwroot
docker build -t todo-db .\db
```

### Создание сети

```powershell
docker network create todo-network
```

### Запуск базы данных

```powershell
docker run -d --name todo-db --network todo-network -p 5432:5432 todo-db
```

### Запуск почтового сервера

```powershell
docker run -d --name todo-mail --network todo-network -p 3025:3025 -p 3110:3110 -p 3143:3143 -e GREENMAIL_OPTS="-Dgreenmail.setup.test.smtp -Dgreenmail.setup.test.imap -Dgreenmail.setup.test.pop3 -Dgreenmail.hostname=0.0.0.0 -Dgreenmail.users=test@local:secret" greenmail/standalone:2.1.8
```

### Запуск backend

```powershell
docker run -d --name todo-back --network todo-network -p 5000:5000 todo-back
```

### Запуск UI

```powershell
docker run -d --name todo-ui --network todo-network -p 8080:80 todo-ui
```

### Пересборка backend после изменений

```powershell
docker rm -f todo-back
docker build -t todo-back .
docker run -d --name todo-back --network todo-network -p 5000:5000 todo-back
```

### Просмотр контейнеров и логов

```powershell
docker ps
docker logs todo-back
docker logs todo-db
docker logs todo-mail
```
